## 问题一：MyBatis-Plus 在非 Spring 工程下抛 `NoClassDefFoundError: GenericTypeResolver`

### 现象
按指导书完成步骤 2.4 后，代码可正常运行；进入步骤 4.3（`EmpPlusMapper extends BaseMapper<Emp>`）
后执行 `mvn clean test`，全部 17 个用例报错：

```
[ERROR] Tests run: 17, Failures: 0, Errors: 17, Skipped: 0
java.lang.NoClassDefFoundError: Could not initialize class com.lab.util.MyBatisUtil
[ERROR]   EmpDynamicSqlTest.testSelectByCondition:26
          NoClassDefFound org/springframework/core/GenericTypeResolver
```

> 说明：第一条触发失败的用例报出**根因** `org/springframework/core/GenericTypeResolver`，
> 其余用例因为 `MyBatisUtil` 静态初始化已经失败，只能报
> `Could not initialize class`（JVM 对类初始化失败后的后续引用不再重复抛原始异常）。

### 排查过程
1. 先怀疑是 `pom.xml` 缺少 MyBatis-Plus 依赖 → `mvn dependency:tree` 显示 MP 三个子模块
   （core / annotation / extension）均已正常解析，排除。
2. 再用脚本遍历本地仓库中的 jar，在 class 常量池里检索 `org/springframework` 字符串：
   ```
   HIT  D:\maven-repository\com\baomidou\mybatis-plus-core\3.5.3.1\mybatis-plus-core-3.5.3.1.jar
         com/baomidou/mybatisplus/core/toolkit/reflect/SpringReflectionHelper.class
   ```
   定位到「谁引用了 Spring」。

### 原因分析
MyBatis-Plus 的 `ReflectionKit` 在解析 `BaseMapper<Emp>` 的泛型实参（用于推导实体类型）时，
会委托 `SpringReflectionHelper` 调用 `org.springframework.core.GenericTypeResolver`。
而 `com.baomidou:mybatis-plus` 这个 artifact **并未把 spring-core 作为传递依赖引入**，
所以在「纯 MyBatis + MP、不用 Spring 容器」的工程里一调用就缺类。

### 解决方案
在 `pom.xml` 显式补充 spring-core（版本与课程实验二的 Spring 5.3.x 对齐）：

```xml
<dependency>
    <groupId>org.springframework</groupId>
    <artifactId>spring-core</artifactId>
    <version>5.3.31</version>
</dependency>
```

补充后重新执行：`Tests run: 17, Failures: 0, Errors: 0` → **BUILD SUCCESS**。

### 收获
`NoClassDefFoundError`/`NoClassDefFoundError: Could not initialize class` 这类错误
往往不是"依赖没引"，而是"**引了但缺了它自己需要的类**"。
用 `dependency:tree` 只能看声明的依赖，必要时需要直接扫 jar 的常量池才能定位真正的引用方。

## 问题二：用原生 `SqlSessionFactoryBuilder` 构建工厂，BaseMapper 方法全部失效

### 现象（已复现，见 `docs/evidence/03-troubleshoot-console.txt`）

```
########## 故障 1：Invalid bound statement (not found) ##########
[现象] 抛出异常：org.apache.ibatis.binding.BindingException
[信息] Invalid bound statement (not found): com.lab.mapper.EmpPlusMapper.selectList
```

### 原因分析
指导书步骤 2.4 使用 `new SqlSessionFactoryBuilder().build(in)`，这在纯 MyBatis 阶段完全正确；
但 `BaseMapper` 的 `selectList / insert / updateById` 等方法**并不是 XML 里的语句**，
而是 MyBatis-Plus 在构建期通过自己的
`MybatisMapperRegistry` → `MybatisMapperAnnotationBuilder` 动态注入到 `MappedStatement` 中的。
原生 `SqlSessionFactoryBuilder` 不会走这条 MP 的扩展链路，于是按 `namespace + id`
去查 `MappedStatement` 时自然找不到。

### 解决方案
统一改用 MP 提供的构建器（`MyBatisUtil` 中的实现）：

```java
SqlSessionFactory factory = new MybatisSqlSessionFactoryBuilder().build(in);
```

它同时兼容手写 XML 映射与 `BaseMapper`，因此 `EmpMapper`（XML）与 `EmpPlusMapper`（BaseMapper）
可以在同一个 `SqlSessionFactory` 下共存。

### 收获
这解释了指导书步骤 4.1 中"将 mybatis 依赖替换（或共存）为 MyBatis-Plus（MP 内置 MyBatis 核心）"
的真正含义——**共存的前提是构建器也要换成 MP 的**，否则两套映射机制只有一套能用。

## 问题三：分页不生效，`selectPage` 返回全量数据

### 现象（已复现，见 `docs/evidence/03-troubleshoot-console.txt`）

```
[DEBUG] com.lab.mapper.EmpMapper.selectAll - ==>  Preparing: SELECT ... FROM emp
[DEBUG] com.lab.mapper.EmpMapper.selectAll - <==      Total: 4
[现象] 未注册插件时查询到的行数 = 4（无 LIMIT 限制，属于全量返回）
```

### 原因分析
MyBatis-Plus 的分页**不是自动的**：`selectPage` 只是把 `Page` 对象塞进参数，
真正负责"拦截 SQL → 改写为带 `LIMIT` 的语句 → 追加 `COUNT` 查询"的是
`PaginationInnerInterceptor`。未注册该拦截器时，SQL 原样执行，所以返回全量。

指导书步骤 4.5 给出了 XML 写法（`<plugins>` 里写 MP 内部类全限定名），
实测这种写法容易因类名书写/版本差异导致插件静默不生效。

### 解决方案
改为在 Java 中注册，直观且不易写错（`MyBatisUtil` 中）：

```java
MybatisPlusInterceptor mpInterceptor = new MybatisPlusInterceptor();
mpInterceptor.addInnerInterceptor(new PaginationInnerInterceptor(DbType.MYSQL));
factory.getConfiguration().addInterceptor(mpInterceptor);
```

验证：`EmpPlusMapperTest#testSelectPage` 断言「第 1 页每页 3 条时 records 恰好 3 条，
且 total(4) > records(3)」，用例通过 → 说明 `LIMIT` 与 `COUNT` 均已生效。

### 收获
排查"分页失效"的思路：**先看 SQL 日志里有没有 `LIMIT`**。
有 `LIMIT` 说明插件生效，问题在参数；没有 `LIMIT` 就是插件没注册。

## 问题四：多条件查询条件列写错，静默返回空结果（无任何报错）

### 现象
在自测步骤 4.4 的 `QueryWrapper` 时，写了：

```java
wrapper.like("emp_name", "工程师")   // ← 条件列写错
        .eq("status", 1)
        .ge("salary", new BigDecimal("9000"));
```

日志显示 SQL 与参数都"很正常"：

```
==>  Preparing: SELECT ... FROM emp WHERE (emp_name LIKE ? AND status = ? AND salary >= ?) ORDER BY salary DESC
==> Parameters: %工程师%(String), 1(Integer), 9000(BigDecimal)
<==      Total: 0
```

记录数 0，但**没有任何异常**。

### 原因分析
`emp` 表中"工程师"出现在 `post`（岗位）列（`Java工程师`、`前端工程师`），
而 `emp_name` 列只有 `张伟 / 李娜 / 王强 / 赵敏`。
`Like` 条件作用在一个不可能命中的列上，SQL 语法完全合法，数据库只会如实返回空集。

### 解决方案
把条件列改为 `post`，并补上更明确的断言信息：

```java
wrapper.like("post", "工程师") ...
Assert.assertFalse("岗位含“工程师”且在职、薪资>=9000 的记录不应为空", list.isEmpty());
```

### 收获
这是**字符串写列名的典型风险**：拼错列名（甚至拼错表名）在执行期不会报错，
只会静默返回空数据，容易误判为"数据没插进去"。
这正是 MyBatis-Plus 推荐 `LambdaQueryWrapper`（`Emp::getPost`）的原因——
方法引用在编译期就能发现字段写错。本次实验两种写法都保留，作为对照。

## 问题五（设计判断）：指导书示例中的 `@TableLogic` 会改变删除语义

### 现象 / 风险
指导书步骤 4.2 的实体类示例在本项目 `status` 字段上加了一行：

```java
@TableLogic            // 逻辑删除标记（本实验可选）
private Integer status;
```

若照抄，MyBatis-Plus 会把 `deleteById` 自动改写为
`UPDATE emp SET status = 0 WHERE emp_id = ? AND status = 1`。

### 原因分析
`@TableLogic` 的语义是"**逻辑删除标记**"（标记后该行对业务不可见），
而本项目 `status` 的业务语义是"**在职(1) / 离职(0)**"。
两者含义不同：一个"离职"的员工并非"被删除"，且在后续实验二做列表分页查询时，
MP 还会自动为所有查询附加 `status = 1` 条件，导致"要查离职员工"根本查不出来。

### 解决方案
**不采用** `@TableLogic`，并在 `Emp.java` 注释中写明理由；
如后续实验需要演示逻辑删除，应另建独立字段（如 `deleted TINYINT DEFAULT 0`）
并单独加注解，避免与业务状态字段混用。

### 收获
AI / 示例代码给出了"能跑"的注解，但**注解语义与业务语义是否一致必须逐行人工判断**。
这是"AI 辅助、人脑主导"最典型的落点。

## 附：其它已修正的小问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 每条 SQL 日志被打印两次 | `rootLogger` 已挂 `console` appender，`com.lab.mapper` logger 又挂了一次 | 去掉 logger 上重复的 appender 声明 |
